Completion reveal does not appear when the after-photo is the finishing action (dead refreshReveal)

high

refreshReveal is declared as a no-op at line 219 and never reassigned, yet it is the only update hook called after photo add/delete in PhotoBlock (lines 213-214). The natural completion path is: work all six steps, then take the after photo. When that last photo is added, onchange runs recomputeDone (done becomes true) + saveProg + paint + refreshReveal(), but never render(), so the RevealCard at the top of ZoneScreen (line 187) never renders. The headline before/after reveal silently fails to show until an unrelated re-render (navigation or a step toggle). The same dead hook leaves a STALE RevealCard and AuditBlock on screen when a user deletes a photo that un-completes an already-done zone.

Fix. Assign refreshReveal to a real re-render inside ZoneScreen (e.g. set refreshReveal = () => render() when ZoneScreen mounts, and reset it to the no-op on go()), or have PhotoBlock's add/delete handlers call render() directly when recomputeDone flips p.done. Simplest: after recomputeDone in both PhotoBlock handlers, if p.done changed, call render().

Diagnostic report leaks the AI proxy hostname despite the in-app claim that it contains no endpoint URL

medium

diagnostic() sets ai_endpoint_host to new URL(endpoint).hostname (line 45) and exposes it on the Diagnostics screen and in the copied/pasted report. The Settings help text (line 288) tells users the report 'contains no photos, no household or room names, and no endpoint URL.' The hostname is part of that URL and can identify a user's self-hosted proxy or infrastructure. For an app whose sensitive asset is home data, a false privacy assurance is worse than the leak itself.

Fix. Either drop ai_endpoint_host from diagnostic() and report only a boolean like ai_configured:true/false, or update the Settings copy to state accurately that the proxy hostname (not the full URL or key) is included. Prefer the boolean so the stated guarantee stays true.

Photo thumbnails and the reveal diptych are not keyboard-operable

medium

Thumbnails (line 213) and the before/after slots use <div role=button> with an onclick but no tabindex and no keydown handler, so they cannot be focused or activated by keyboard or by switch-access users. On a phone this also means assistive tech like Full Keyboard Access and external-keyboard users cannot open or delete a photo. The 'View photo' aria-label promises a control that keyboard users cannot reach.

Fix. Render these as real <button> elements (they already carry no layout that forbids it) or add tabindex=0 plus a keydown handler for Enter/Space. Reusing the existing <button> styling would also inherit the larger tap targets you added elsewhere.

Cancelling an AI call is reported to the user as a failure/timeout

low

The Cancel button calls aiCtrl.abort() (lines 231, 261). classifyAI (line 92) maps every AbortError to 'timeout', and the catch path renders errRow('That did not go through (timeout).', retry). A user who deliberately cancelled is told the request failed and is offered a retry, which is confusing and reads as an error state for an intentional action.

Fix. Track an explicit cancel flag (set it in the Cancel onclick before abort) or check it in the catch; when the abort was user-initiated, quietly return to the pre-request state (offstate or the Build/Get button) with no error row, reserving the 'timeout' message for the 60s auto-abort.

callAI never checks response.ok, so non-JSON HTTP errors are misclassified

low

callAI (lines 97-98) calls await r.json() without checking r.ok. A proxy that returns a 500/502 with an HTML or empty body throws a SyntaxError on r.json(); classifyAI then falls through to the default 'http_error' with no status context, and a gateway 504 is indistinguishable from a JSON parse problem in the diagnostic events.

Fix. After fetch, if (!r.ok) read r.status and throw new Error('http_error '+r.status) before attempting r.json(); guard r.json() in its own try so a non-JSON body yields a clear network/http classification rather than a parse_failure.

Session time under-reports during long single-zone work and is lost on a hard tab kill

Fix. Add a low-frequency interval (e.g. accrueTime every 30-60s while curZone is set) and also flush on the pagehide event, which is more reliable than beforeunload on mobile Safari/Chrome.

Surface the EXIF/GPS-stripping you already do as an explicit privacy assurance. compress() (line 80) and aiShrink() (line 90) both re-encode through a canvas and toDataURL, which strips EXIF including GPS coordinates before anything is stored or sent to the proxy. That is a genuine privacy win for photos of people's homes but it is invisible to the user. State it near the photo fineprint and in the README ('location and camera metadata are removed on-device before storage or AI'), and add a one-line per-send note when photos leave the device for AI so consent is informed.

Add a clear, dismissible 'photos are leaving your device' confirmation before the first AI call. Right now tapping Build my Sort plan or Get my review sends home photos to a configured proxy with no distinct moment of consent beyond the static fineprint. A first-use interstitial that names the destination host and lets the user confirm (once per session or once ever) respects the sensitivity of home imagery and matches the P0 consent items the README defers to the native shell.

Replace native confirm()/alert() with in-app modals. Photo delete (line 279) and Erase everything (line 289) use window.confirm, and storage-full uses toast. Installed PWAs and some mobile browsers render or suppress native dialogs inconsistently, and confirm() blocks the main thread. You already have a sheet/lightbox modal system; route destructive confirmations through it for consistent styling, larger tap targets, and reliable behavior on the home-screen app.

Preserve scroll intent when the RevealCard is inserted at the top on completion. When the final step is marked done, render() preserves scrollY (line 127), but RevealCard is prepended (line 187), pushing existing content down so the restored scroll position now points at the wrong content and the reveal itself may be off-screen. On zone completion specifically, scroll the reveal into view (or reset to top) rather than restoring the pre-render offset, so the payoff moment is actually seen.

Show live elapsed time and a lightweight autosave indicator on the zone screen. The zone runner shows only the estimated duration (sum of z.t), never the measured spentMs the app now tracks. A small 'X min on this zone' readout that updates as time accrues would make the new session-time instrumentation visible where the work happens and reinforce the Lean framing of measured effort.

Give the Diagnostics/events view a purge and an on-device-only reminder. Events are capped at 600 and cleared by Erase everything, but there is no standalone 'clear diagnostics' affordance and no statement of retention. Add a Clear events button on the Diagnostics screen and a one-line note that events never leave the device unless the user copies the report, so power users can reset instrumentation without wiping progress.

User-initiated cancel is recorded as a timeout

medium

Cancel calls aiCtrl.abort(), which raises AbortError; classifyAI (line 92) maps AbortError to 'timeout'. The same class is used for the real 60s timeout. So ai_call_failed{error_class:'timeout'} conflates deliberate cancels with genuine network timeouts, corrupting the AI reliability metric, and the UI tells a user who just cancelled 'That did not go through (timeout).'

ai_latency_ms is logged even when JSON parsing subsequently fails

low

In callAI (line 100) logEvent('ai_latency_ms') runs before extractJson is called on the same line. If extractJson throws (parse_failure), latency is logged AND ai_call_failed is logged, so count(ai_latency_ms) does not equal count(successful plans). Anyone deriving AI success rate from latency-sample count will overstate success.

Fix. Move the ai_latency_ms log to after a successful parse, or add a separate ai_call_succeeded event that fires only on a fully parsed result, and document that ai_latency_ms is a transport-only signal.

Unbounded audit log and silent event drop create pre-flush data loss

low

p.auditLog (line 268) grows without bound inside prog and is persisted on every audit, and the events buffer silently shift()s the oldest entries past 600 (line 40). Both live only in localStorage with no flush. Before any backend exists, a heavy user loses the oldest events and bloats prog, and there is no record that data was dropped.

Fix. Cap auditLog to the last N entries (keep an aggregate count separately), and replace the blind ring-buffer with an outbox that tracks a flushed offset so unsent events are preserved and only acknowledged ones are pruned; emit an events_truncated counter when forced to drop.

Make the event schema backend-ready before you need it. To flush to a real analytics service later you need three things the current records lack: a stable sessionId minted at app_open, a per-event id (a genId-style idempotency key) so retried batches dedup server-side, and a schema_version plus app_version stamped on each event or batch. Add these now while volume is tiny. The existing {t,e,props} shape already gives you ordering via t; adding id+session+version turns it into a resumable, dedupable stream.

Gate any network flush behind explicit opt-in consent. The README lists privacy policy and consent as unbuilt P0 items, and the sensitive asset is photos of people's homes. Even though events are photo-free, sending anything off-device must be opt-in. Add a persisted analytics_consent flag (default false), keep all instrumentation on-device until it is set, and make the flusher a no-op without it. This keeps the honest on-device posture and cleanly separates 'collected locally' from 'transmitted'.

Capture uncaught errors, not just render errors. The error boundary only wraps renderInner. Add window.addEventListener('error') and ('unhandledrejection') handlers that log app_error with a coarse error_class (and no message text, to stay PII-safe). Async failures in photo/IDB/AI paths currently vanish from telemetry; these listeners make your reliability picture honest without leaking stack contents.

Enrich the completion event for product insight. zone_completed should carry ai_used (was a Sort plan or coach review run), photos_before/after counts, and steps-substeps completion depth. This lets you answer whether AI drives completion and where users stall, all from counts with zero added PII. Pair with a distinct ai_call_cancelled outcome so cancels are a visible product signal rather than noise in the failure bucket.

Centralize event names and enforce a payload allowlist. Define a small frozen registry of event names and, per event, the allowed prop keys (all scalar counts/enums). Have logEvent drop or warn on any key not in the allowlist. This is the cheapest durable guarantee that a future contributor cannot accidentally add a free-text note, a room name, or a URL to a payload that later gets flushed off-device.

Diagnostic: add a generated_at stamp, a rolling window, and a file export. Add generated_at to diagnostic() so pasted reports are time-anchored, compute the error counts over a recent window (not all-time) so a single old failure does not look chronic, and offer a download-as-file option alongside clipboard for users whose clipboard is blocked. Keep the redaction of host/names as the default, with any host inclusion behind an explicit toggle.
