Section 0The constraint that shapes everything

Everything in the app already runs on-device: state, photos, the six-step engine, the product catalog, the Sustain audit. The only thing that reaches out is AI, and the app has exactly two AI calls, both of which look at photos:

  • Analyze before → a clutter score, a Sort plan, and a list of visible hazards.
  • Review after → a score against the standard, coaching, wins, and what remains.
The hard truth These are vision tasks. On-device text models are mature and easy to reach on both platforms. On-device vision-language is where the platforms diverge: Android's Gemini Nano has emerging image input, while Apple's on-device model is text-only and needs a separate image pipeline in front of it. Plan around capability detection and fallback, never around parity.

A 2 to 4 billion parameter on-device model can reliably judge "this surface is cluttered, here is a sensible order of attack" and produce warm, useful coaching. It will be weaker than the cloud model at the sharp, safety-critical calls (spotting a looped blind cord, a specific tip-over risk). So the goal is not to replace the cloud model everywhere. The goal is a genuinely good offline, private tier that most users can run, with the cloud proxy still available for best-in-class quality.

Section 1Target architecture

The current build already isolates every AI call behind a single callAI() function with a configurable transport. Keep that seam. In the Expo app it becomes a provider interface with three tiers and per-task routing.

Three tiers, chosen per call

  1. On-device (preferred when capable): private, offline, free, no photo egress.
  2. Cloud proxy (the existing key-holding proxy): best quality, requires network and the zero-retention proxy.
  3. Static guidance (already built): the deterministic built-in guidance that ships today. Always the floor; never an error state.

Routing rule (per task, not per app):

resolveProvider(task, deviceCaps, settings):
  if settings.aiMode == "off"            -> static
  if settings.aiMode == "device":
      if deviceCaps.canDo(task)          -> on-device
      else if settings.cloudEndpoint     -> cloud     (with consent)
      else                               -> static
  if settings.aiMode == "cloud":
      if settings.cloudEndpoint          -> cloud     (with consent)
      else                               -> static

Because vision support is uneven, deviceCaps.canDo(task) is task-aware. A device might handle the text-shaped parts of coaching on-device but route the raw-photo scoring to the cloud. The user sees one toggle; the routing handles the nuance.

What carries over from the prototype The strict JSON contracts (clutter_score, plan, hazards / score, coach, wins, remaining), the extractJson / repairParse tolerant parser, the off-state copy, and the one-time photo-send consent gate. On-device makes the consent moot (nothing leaves the phone), which becomes a feature, not a step to remove.

Section 2Android: Gemini Nano

Gemini Nano is Google's on-device model. Your app does not bundle it; it is delivered and updated by AICore, a system service, and shared across apps. That keeps your download small but ties you to device support and to the model version AICore provides.

Two ways to reach it

Access pathWhat it gives youFit for 6S
ML Kit GenAI APIs
(higher level)		 Task APIs: summarization, rewriting, proofreading, and image description (an on-device caption of a photo). Image Description is the practical foothold: caption the before photo on-device, then reason over the caption for the plan and hazards.
Google AI Edge SDK
com.google.ai.edge.aicore (lower level)		 A generateContent style call against Nano. Free-form prompting; multimodal image input is emerging on newer Nano versions and devices. Preferred once multimodal input is dependable on your target devices; until then, pair it with the Image Description output as the image channel.
Device reality Nano runs only on a subset of premium phones (recent Pixel and Galaxy S flagships, with the set widening over time), and the feature requires an on-device download managed by AICore. Always gate on a runtime availability check and fall back. Never assume Nano is present.

Kotlin shape (verify against current SDK)

// Availability first — Nano is not on most devices.
val status = generativeModel.checkStatus()   // AVAILABLE / DOWNLOADABLE / UNAVAILABLE

// Text-shaped reasoning over an on-device image caption:
val caption = imageDescriber.describe(beforeBitmap)      // ML Kit GenAI
val prompt  = buildSortPrompt(zone, caption)             // your existing prompt, image -> caption
val result  = generativeModel.generateContent(prompt)    // Google AI Edge SDK
val json    = repairParse(result.text)                   // ported tolerant parser

Broader device coverage (mid-range Androids that lack Nano) is where a bundled model comes in; see Section 4, Option B.

Section 3iOS: Apple Foundation Models + Vision

Apple's on-device model is exposed through the Foundation Models framework. It is an approximately 3-billion-parameter model that powers Apple Intelligence, with a clean Swift API, and critically for us, guided generation (typed, schema-constrained output). The catch: it is a language model. It does not take an image as input.

The iOS pattern for photo tasks Use the Vision framework as the eyes and Foundation Models as the voice. Vision runs on-device and produces structured signals from the photo (object and scene labels with confidences, text via OCR, a saliency or objectness map you can turn into a rough clutter measure). Feed those signals as text into a Foundation Models session with a typed output schema. The language model never sees pixels; it reasons over Vision's structured read of them.

What Vision gives the model

  • Scene / object labels (classification and object detection) with confidences, a text list of what is in frame.
  • Saliency / objectness maps, from which you can derive a simple surface-coverage or clutter proxy.
  • Recognized text (OCR), useful for labels, mail, and paperwork piles.

This is coarser than a true vision-language model, and it will miss subtle safety hazards, so those specific calls are strong candidates to route to the cloud tier. But for clutter scoring and Sort planning it is genuinely serviceable and fully offline.

Swift shape (verify against current framework)

import FoundationModels
import Vision

// 1. Availability — needs an Apple Intelligence capable device.
guard case .available = SystemLanguageModel.default.availability else { return .fallbackToCloudOrStatic }

// 2. Vision reads the photo on-device -> structured features.
let features = try await visionFeatures(from: beforeImage)   // labels, counts, clutter proxy, OCR

// 3. Guided generation returns your exact schema, no fragile parsing.
@Generable struct SortPlan {
  @Guide(description:"0-5 clutter score") var clutterScore: Int
  @Guide(description:"ordered Sort steps") var plan: [String]
  @Guide(description:"visible safety hazards") var hazards: [String]
}
let session = LanguageModelSession(instructions: sortInstructions)
let plan = try await session.respond(to: sortPrompt(zone, features), generating: SortPlan.self)
Device reality Foundation Models requires an Apple Intelligence capable device (iPhone 15 Pro and later, plus M-series iPad and Mac). On older supported iPhones the on-device model is unavailable and the app falls back to cloud or static. Gate on the availability check every time.

Section 4The vision gap: two options

The friction is entirely about vision. Text-shaped work runs beautifully on-device on both platforms; the photo-native scoring does not, uniformly. There are two ways to close that, and they are not mutually exclusive.

Option A: OS models + Vision front-end recommended first

Use Gemini Nano on Android and Foundation Models on iOS, each fed by the platform's image pipeline (ML Kit Image Description on Android, Vision framework on iOS). Route the hardest safety calls to the cloud tier when the user allows it.

  • Pros: smallest app size (no bundled weights), OS-managed updates, best battery and thermal behavior, ships fastest.
  • Cons: fragmented device support, two different image pipelines to maintain, and the on-device vision read is coarse.

Option B: bundle one cross-platform multimodal model later, if warranted

Ship a single small vision-language model (for example a Gemma-class multimodal model) and run it identically on both platforms through an on-device runtime such as MediaPipe LLM Inference, ExecuTorch (with its React Native bindings), or a llama.cpp-based module. One model, one prompt path, one behavior, and real image understanding rather than a caption.

  • Pros: uniform behavior across platforms, works on far more devices, a true VLM (sees the photo), no dependence on OS model availability.
  • Cons: adds one to several GB to the app or a first-run download, you own the performance and battery tuning, and it is meaningfully more engineering.
Recommendation Ship Option A behind the existing AI toggle, with the cloud proxy as the quality tier and static guidance as the floor. Instrument how often each tier is used and how device users rate the results (the event taxonomy and the want_ai signal already exist for exactly this). If on-device demand is real and device fragmentation is hurting coverage, add Option B as a downloadable "high-accuracy offline" pack. Let the data decide whether the bundled VLM is worth its size.

Section 5Getting strict JSON from small models

The app depends on structured output. Small models are weaker at emitting clean JSON on demand, so lean on the platform and on defensive parsing rather than trusting the model.

  • iOS: use Foundation Models guided generation (typed @Generable structs). The schema is enforced, so parsing is essentially free and reliable.
  • Android: Nano has no strict guided-generation guarantee today. Constrain hard in the prompt, request a single JSON object, and run the ported extractJson / balanceClose / repairParse chain. Retry once on a parse miss.
  • Both: keep the schemas small and flat. Fewer fields and shallow shapes raise the hit rate on small models. Your current schemas are already close to this; resist growing them for the device tier.
  • Degrade gracefully: a parse failure is not an error screen. It falls through to static guidance, exactly as the prototype does, and logs a health event with the class only.

Section 7The privacy win

On-device inference turns the app's biggest compliance liability into its strongest selling point. Home photos are sensitive; the whole reason the cloud tier needs a zero-retention proxy and a consent gate is that the images leave the phone. On-device, they do not.

  • Lead with it: "Your home photos never leave your phone" is a headline most home-organizing apps cannot honestly make.
  • The consent gate becomes conditional: required for the cloud tier, silent and unnecessary for the on-device tier. Show it only when a call would actually transmit an image.
  • Store review friction drops: an on-device default sidesteps much of the data-handling scrutiny that the cloud path invites.
  • It also unblocks offline use entirely, which suits a phone-in-hand, room-by-room task where signal may be poor.

Section 8Phased rollout

  1. Seam and interface. In the Expo app, formalize the LocalAI provider interface (appendix) and the three-tier router. Wire the existing static and cloud tiers to it first, with no on-device model yet. This is a pure refactor and fully testable.
  2. iOS on-device (text path). Add the Foundation Models provider for the coaching and text tasks, with guided generation. Ship behind the toggle to Apple Intelligence devices. Lowest-risk first win, and the guided output is reliable.
  3. iOS on-device (photo path). Add the Vision front-end for clutter and Sort. Keep safety on cloud. Measure quality against cloud on the same photos.
  4. Android on-device. Add the Nano provider (ML Kit Image Description plus Google AI Edge SDK), same task routing. Gate on AICore availability.
  5. Evaluate Option B. Review tier-usage and satisfaction telemetry. If device fragmentation or vision quality is limiting, prototype a bundled multimodal model as a downloadable high-accuracy pack.
Expo specifics All of this needs native modules (Expo Modules API, Swift and Kotlin) and an EAS dev build; none of it runs in Expo Go. Each platform provider is a config plugin plus a thin native module exposing one async generate method to JS. Check for maintained community modules (on-device LLM and ML Kit wrappers exist) before writing your own, but expect to wrap at least the newest OS APIs yourself.

Section 9Risks & open questions

  • Fast-moving APIs. Foundation Models, ML Kit GenAI, and the Google AI Edge SDK are all young and changing. Every code shape here is directional; confirm signatures, availability checks, and multimodal support against current docs when you build.
  • Multimodal on Nano. Whether free-form image input is dependable on your specific target devices is the key unknown on Android. The Image Description fallback de-risks it, but validate on real hardware early.
  • Quality bar for safety. Decide the policy explicitly: never let a weak on-device pass silently replace a safety review. Either route safety to cloud or clearly label the on-device safety pass as a lighter check.
  • Battery and thermals. Vision plus LLM per photo is heavy. Debounce, cache results per photo, and never run inference speculatively.
  • Consistency across tiers. Scores from three different engines should not swing wildly for the same photo. Calibrate the on-device scoring against the cloud tier so the number feels stable if a user switches modes.
  • App size vs coverage (Option B). A bundled VLM is the only way to reach non-premium devices with true vision, but the size cost is real. Make it opt-in, not default.

AppendixThe JS interface

One interface the JS calls; native providers implement it per platform. This is the contract that lets the router stay simple and the tiers stay swappable.

interface LocalAIProvider {
  // Cheap, cached capability probe. Task-aware because vision != text.
  availability(task: "sort" | "coach" | "text"):
      Promise<"available" | "downloadable" | "unavailable">;

  // The one call. Images are on-device URIs; the provider decides how to
  // consume them (caption on Android, Vision features on iOS, pixels for a
  // bundled VLM). Returns the app's existing strict schema for the task.
  generate(req: {
    task: "sort" | "coach" | "text";
    prompt: string;              // reuse the ported prompt builders
    imageUris?: string[];        // local file URIs, never uploaded
    schema: JsonSchema;          // small, flat, per task
  }): Promise<object>;           // parsed + validated, or throws -> fallback
}

// The router picks a provider per call; callAI() in the ported core stays
// the single seam, exactly as in the PWA prototype.
