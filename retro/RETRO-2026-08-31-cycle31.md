# Retrospective, cycle 31 (2026-08-31)

## What this cycle did

Answered the question the MCP failure raised: **what would tell me an
integration had stopped?** For the ones sitting behind our own domain, the
answer was nothing at all.

**Umami and Listmonk are now asked for proof they are themselves.** Both are
reverse proxy hops, and a proxy fails happily at 200: an error page, a login
redirect, an empty body with a success code. Nothing here asked them for more
than a status code, which is the same gap that let a deactivated Stripe link,
three 403 directories and a twelve day MCP failure all read as healthy.

Each check now asks for something only the real service can produce. Umami's
tracker is minified JavaScript reading screen, navigator and doNotTrack, which
no login page contains. Listmonk's public form carries its own markup. The
beacon endpoint must refuse a GET. And the analytics site id the live pages send
must match the one this repository ships, or events are being counted against
some other site, or none. All four pass.

**The cloud routines are healthy, and better than the GitHub ones.** The
6S Success hourly operator fired at 13:43 and succeeded, with the next run at
14:43: genuine hourly cadence. Yesterday's finding was that GitHub Actions drops
about three quarters of its scheduled triggers. So the reliable scheduler was
already here, and the unreliable one is the one I spent yesterday tuning.

## What went well

**Proven in all three directions before being trusted.** Pointed at a host that
answers 200 to everything it reports broken and names which checks failed;
pointed at an unreachable host it reports unknown and says the integrations were
not checked, never that they work.

**I chose not to prove more than I safely could.** A synthetic pageview and a
test subscription would each prove the full path end to end. Both would also
write junk into data Phil reads: a fake visit into an analytics set holding
almost nothing, and a fake address onto a mailing list. A check that damages
what it measures is not worth the extra certainty, and that reasoning is in the
file rather than in my head.

**A weakness is recorded rather than hidden.** The beacon check passes against
any host that returns 404, so it can catch a misconfigured proxy but cannot
confirm Umami is behind it. Saying so in the docstring is worth more than the
check pretending to be stronger than it is.

## What did not go well

**I could not verify the thing that actually matters.** Every check here proves
the plumbing is connected. None proves a single pageview has ever been recorded,
because that needs Umami's own credentials. So "analytics works" still means
"analytics is reachable and is really Umami", and the deck should not be read as
more than that.

**Another of Phil's routines has been dead for three months and nobody noticed.**
Nightly Benchmark Research was auto disabled in May for repository access. It
belongs to a different business so it is not mine to restart, but it is the
third time this week that something stopped silently, and it was visible the
moment I asked rather than assumed.

**Still nothing that moves revenue.** Better instruments again. The shop remains
10 of 159 products with every payment link dead.

## What to change next cycle

1. **Ask for credentials that would let a check see the far side.** Umami's API
   key would turn "analytics is reachable" into "analytics recorded N visits
   this week", which is the difference between plumbing and a number.

2. **Prefer the cloud routine to the GitHub schedule for anything that must
   actually happen.** One achieves hourly, the other achieves a quarter of it.

3. **Stop building checks for a week unless one is load bearing.** Nine of the
   last twelve cycles ended with a new gate. The gates are good and the shop
   still cannot take money.
