# Retrospective, cycle 37 (2026-08-31)

## What this cycle did

Went to the web looking for a maintainability problem and found a customer
facing one.

The plan was to give the footer a single source, on the grounds that 186
identical copies with no owner is the duplicate drift I have removed everywhere
else. Checking that premise first showed it was half wrong: three generators
already lift their chrome from resources.html, so there is a source in practice.

What there is not is enforcement, and the gap had already been paid for. **All
28 legacy article pages carry a footer missing "The Entryway Deck".** One of the
things we sell was unlinked from every article on the site, and articles are the
SEO landing pages, which makes those exactly the pages search brings people to.

`build_articles.py` owns two of the thirty articles. The other 28 are older hand
written pages no generator rewrites, so they kept whatever footer was canonical
the day they were made. Running the generator does not touch them, which I
confirmed by running it rather than reasoning about it.

## What went well

**Checking the premise turned a chore into a find.** Had I gone straight to
refactoring, I would have built a templating step and never noticed that a
product was missing from navigation on 28 pages.

**The fix is enforced, not just applied.** A static site cannot template a
footer without a build step, and adding one to fix a copy defect is a large
change for a small reason. resources.html is already the source in practice, so
the new gate makes that enforcement. It normalises the ../ prefix rather than
treating a correct relative path as drift.

**Two exceptions are named with their reasons.** invest.html has its own minimal
legal footer and the print and play page is a redirect notice. Left unnamed,
this gate would have warned about two intentional pages for ever, which is how
a check stops being read. I have fixed that exact failure in the stale-claims
gate before and did not want to recreate it.

**Verified in four ways before claiming it:** no page missing the link, every
footer link resolving from articles/, the pages rendering clean at 360 and 390,
and all 184 sitemap URLs still resolving.

## What did not go well

**I ran half a documented pipeline and read the result as a defect.** Running
`build_articles.py` alone stripped the `?v=` fingerprint from measure.js across
187 pages. That looked like a regression in the generator. It is not: that
generator writes bare asset paths and `fingerprint_assets.py` is the pass that
stamps them, which is documented in the ownership gate's own comment. I have now
made this mistake twice in a fortnight, both times by running one generator
instead of the chain.

**The defect was eight days old at minimum and probably much older.** Nothing
was watching, and I have run the mobile sweep, the URL checker, the page audit
and the catalogue audit over these pages repeatedly without any of them looking
at whether the footers agreed with each other.

**Cycle sixteen, no revenue movement.** Day eight.

## What to change next cycle

1. **Never run a single generator. Run the chain, or run the gate.** Twice now.
   The ownership gate exists precisely because the order matters.

2. **Ask what else has no owner.** The 28 articles were unowned by any
   generator, which is why they rotted quietly. That question is worth asking
   of every directory, not just this one.

3. **Compare like things to each other, not just to a rule.** Every check I run
   compares a page to a standard. This defect was only visible by comparing two
   pages to each other, and that is a different kind of question.
