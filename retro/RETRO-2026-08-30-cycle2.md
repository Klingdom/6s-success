# Retrospective, second cycle ending 2026-08-30

Four commits. Two P0 issues that had been labelled blocked-on-art for weeks
turned out to be half text problems, and nobody had checked the text.

---

## What went well

**The capability built last cycle paid for itself immediately.** The zone hero
work existed to put pictures on 114 pages. What it actually produced was a
working local image pipeline, and the two oldest P0 issues in the queue were
both labelled blocked-on-art. They had been blocked on a thing that stopped
being true. Nothing in the issue tracker knew that, because an issue records
the state of the world on the day it was written.

**Reading the issues found defects the issues did not mention.** Both P0s were
about pictures. Opening the corpus those pictures get their words from showed
"Set in Order", the rejected name for the second S, in sixteen `six_s_lesson`
lines, already rendering onto finished cards. EE-001's title was still
`AMAZON DELIVERY` in that same file, months after the image file, the card
list, the master proof and the ALT text had all been renamed to Delivery Day.
The text layer was simply never in that sweep.

**The architecture fix beat the ticket.** Issue #2 asked for 17 stale images to
be regenerated. Doing that would have left the deck in the architecture that
produced them: every word baked into pixels, so garbled lettering, a fake QR
code and a retired friction meter are all unreachable by any text sweep.
Fixing 17 pictures does not stop the 18th. The whole deck now renders from a
hero photograph with no text plus real type, which is what the deck's own
prompt kit had prescribed and what had never been run.

**Fixing at source, not at the symptom.** The corpus is generated by
`ops/merge_cardtext.py` from six batch files, so correcting the corpus alone
would have been undone by the next merge. Those batches were also gitignored,
which meant 88 hand transcribed cards, the only copy of that reading, lived on
one laptop while the file they generate was tracked. Moved into `ops/`.

**Review carried over without being re-argued.** Last cycle's rule, that
unjudged counts as rejected and an approval is bound to the image's sha, was
applied to 88 card heroes without redesigning it. Generalising
`ops/review_heroes.py` to named sets was the right call over copying it a
third time, because the copy is what drifts.

## What did not go well

**The dashboard reported a clean zero the entire time.** The Canon defects row
read "0 live uses of the rejected term" while sixteen of them sat in the file
the renderer reads. It was counting honestly, in the deck's HTML documents,
and never looked at the JSON. This is the **fifth** instance of the same
defect in this repository, and the second in two cycles: a check that reports
"I found nothing" when what happened is "I did not look."

I have now written the same lesson into two consecutive retrospectives. That
is a sign the lesson is not being applied at the point where it would help,
which is when a check is first written, not when it is caught misleading
somebody.

**A test I wrote destroyed the fix I had just made.** To prove the new gate
could fail I injected the banned term into the corpus, then reverted with
`git checkout`. The corpus was tracked, so the revert took my correction with
it. Caught by re-reading the grep count rather than by trusting the sequence,
but only because I happened to look.

**The second prompt pass was worth much less than the first.** 56 of 88 passed
first time. Rewriting the 29 failures recovered 11. The remaining 17 are not
one more pass away: they need legible labels, which the negative prompt
suppresses deliberately because that suppression is what keeps garbled text
out of the deck. That is a real constraint of this tool, not a prompt I have
not thought of yet.

**EE-001 took three attempts, and the first two failed the same way.** Both
named the front door. The model painted the door and dropped the boxes. The
door is the strongest entryway cue in its training and wins every competition
it is entered into. I could have known that after the first failure.

---

## What to change next cycle

**A new check must state what it looked at.** Every gate and every dashboard
count should name its inputs in its own output, so "0 across 6 files" is
distinguishable from "0". Both defects this cycle would have been visible on
sight. This is the rule that replaces writing the same retrospective entry a
third time.

**Prove a zero before trusting it.** Done twice this cycle: the corpus gate and
the canon counter were both shown going red before being believed. A zero that
has been demonstrated to be capable of becoming a one is evidence. One that
has not is a hypothesis.

**Never revert with git checkout during a test on a tracked file.** Copy the
file aside, or make the test edit in a scratch copy. The revert is not scoped
to the test.

**One dominant object per generated prompt.** Every card that failed twice had
two nouns competing, and the more famous noun won every time.
