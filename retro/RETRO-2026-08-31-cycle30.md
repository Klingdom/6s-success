# Retrospective, cycle 30 (2026-08-31)

## What this cycle did

Phil reported that publishing seemed to be failing. It was, in a way neither of
us had seen, and the diagnosis mattered more than any of the fixes.

**Git was never the problem.** Local and origin were identical, and I measured
that before touching anything. Three real things were broken:

1. **The build was red, and it was mine.** My cycle 29 retrospective carried
   three em dashes, which the house style forbids.
2. **"Publish MCP image" had been failing since 19 August, twelve days.** Its
   own gate correctly refuses to ship when `mcp/content.json` drifts from the
   manual it is copied from; the manual was updated on 25 August and nothing
   re-copied it.
3. **GitHub is dropping about three quarters of the scheduled runs.** The
   hourly brief managed 12 runs in 51 hours against a schedule of every hour.

Then I generalised the second one: **161 duplicated filenames across the
repository, 123 of them already drifted.**

## What went well

**I measured before believing the report.** "Pushes are failing" was the
symptom; pushes were fine. Had I taken it at face value I would have spent the
cycle on git remotes and never found the MCP failure.

**Each candidate cause was eliminated with evidence, not reasoning.** For the
dropped schedules: not quota (public repo, free minutes), not long runs (every
run under 90 seconds), not `cancel-in-progress` (all false), not a broken job
(the email log carries a real `sent <message-id>`). Only then did I conclude it
was cron contention, and I said "mitigation, not guarantee" rather than
promising a cadence the platform does not offer.

**Twice I nearly fixed something deliberate, and read the documentation
first.** The agents live in `claude/` rather than `.claude/`, which looks like
a mistake that would stop them loading; the README explains it prevents
defining all 14 twice at both scopes. And the estate mirror looked like an
accident until its commit message showed it was created on purpose.

**I decided not to add a gate.** A permanent warning about 123 files that are a
snapshot by design would cry wolf, which is precisely the defect I removed from
the stale-claims gate a week ago. Restraint was the right call and I want it on
the record as a decision rather than an omission.

## What did not go well

**A whole publishing pipeline failed silently for twelve days.** The reason is
the uncomfortable part: it triggers only on changes under `mcp/`, nothing
touched that directory, so it barely ran, and when it did the failure was one
line in a list nobody reads. **It surfaced by accident**, because I edited its
workflow file for an unrelated reason. If I had not been adding timeouts today,
it would still be broken.

**I guessed twice at things I could have measured, and was wrong both times.**
I read a separator character as an em dash and built a tidy house-style
explanation around it; the count in both files was zero and it was a `→` the
console could not render. Then I guessed at gh's wording for a never-run
workflow, twice, before running the command and reading the actual 404.

**I broke my own rule again.** Cycle 23 recorded "stop using heredocs for
anything containing a backslash". I used one for a `\r\n` literal and got a
syntax error. The pre-commit hook I built this cycle would not have caught it,
because that failure was loud.

## What to change next cycle

1. **Ask what would tell me a pipeline had stopped.** The MCP failure was
   invisible because nothing watched it. `gate_workflows_healthy` covers
   workflows now. The same question is unanswered for the cloud routines, the
   Stripe webhook, and the Listmonk proxy.

2. **When a character does not render, print its codepoint before theorising.**
   One command would have replaced a wrong explanation with the right one.

3. **Two guesses is the limit.** After the second wrong guess about gh's
   output I should have run the command immediately rather than a third time.
