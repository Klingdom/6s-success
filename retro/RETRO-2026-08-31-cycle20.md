# Retrospective, cycle 20 (2026-08-31)

## What this cycle did

Turned the new mobile harness on the generated pages, then followed what it
found into the server layer.

**Three directories were answering 403 Forbidden on the live site.** `/rooms/`,
`/deck/` and `/downloads/`. `/zones/` and `/articles/` answered 200. The only
difference between them is whether the directory happens to contain an
`index.html`: without one, `try_files` falls through to the directory,
`autoindex` is off, and nginx says Forbidden. That is the wrong answer twice
over, because nothing is being withheld, and because "Forbidden" is an alarming
thing for a shop to say to a visitor or a crawler.

`/rooms/` now redirects to `resources.html`, which is already the rooms hub, and
`/deck/` to `deck.html`. Everything else that would have 403'd is now an honest
404 on our own page.

**I deliberately did not build a rooms index.** It was the obvious move and it
would have been wrong: `resources.html` already lists every room, so a second
page would be a duplicate competing with it for the same intent, which
CLAUDE.md §50 exists to prevent. A redirect was the smaller and more correct
change.

## What went well

**CI now checks what the site returns, not just whether it parses.** This is the
real outcome of the cycle. `nginx -t` was already run in two places, so a config
that cannot start has never been able to ship, but parsing is not answering.
Nothing in this repository had ever asked the running server a question, and
three wrong status codes sat on the live site while every gate passed. CI now
builds the image, starts it, and asserts thirteen real status codes over HTTP
*before* the push, so an image that answers wrongly is never published. All
thirteen passed on the first run.

Two of those checks matter commercially and nearly got missed: now that
`/downloads/` returns 404, the files *inside* it must still serve, because that
is what a paying customer is sent after buying.

**I verified in the right place when the local one was unavailable.** Docker
Desktop would not start here, so the nginx change went to CI unverified by me
but unable to reach production without passing. That is a reasonable division:
the Dockerfile's own `nginx -t` means a broken config fails the build rather
than the deploy.

**The sweep of generated pages came back clean**, which is genuine information
rather than a null result: zone, room, article and deck-gallery templates all
hold at 360px, so the previous cycle's fixes did not have a template-shaped
blind spot behind them.

## What did not go well

**A heredoc ate a level of backslashes for the fourth time in this project.**
It turned `\b` into a literal 0x08 byte and the `\1` backreference into 0x01
inside a new regex. The pattern then matched nothing, so the change read as
"my fix didn't work" rather than "my fix is corrupt", and I spent a diagnosis
on it. Two control characters were sitting in `preflight.py`, the file that
runs every other gate.

I know this failure. It is in my own notes with the remedy attached, which is to
write a file instead of piping a heredoc. I reached for the heredoc anyway
because it is one line shorter.

**I nearly ignored a warning that was telling the truth about being wrong.**
The stale-claims gate had been reporting three hits for days. Two were real
copy and still true. The third was a *JavaScript comment* in `contact.html`,
scanned because the gate strips HTML tags but not script bodies. A warning that
cries wolf is one I start skimming, and this gate exists to catch something that
actually happened: "most of the range is still in development" surviving on the
homepage past the day 155 products went live.

**I found the 403s by accident.** They surfaced because `shoot_mobile.py`
printed `MISSING` for `site/rooms/index.html`, a page I had listed on a guess.
Nothing was looking for this. The class of defect, "what does each public URL
actually return", had no owner until this cycle.

**A defect in my own week-old tool**: three different `index.html` pages all
wrote to `shots/index-390.png`, so any sweep covering more than one kept only
the last screenshot and silently destroyed the evidence for the others. Same
family as everything else this week: a tool quietly producing less than it
claimed to.

## What to change next cycle

1. **Never pipe a patch through a heredoc again.** Write the file. The rule
   already existed; what was missing was an assertion, so the repair script now
   refuses to save a file containing control bytes. Add that assertion to
   anything that rewrites source.

2. **Ask every public URL what it returns, not just the pages I remember.**
   The CI smoke test covers thirteen. The sitemap has hundreds. A periodic
   sweep of the sitemap against the running image would catch the next 403
   without me stumbling into it.

3. **When a warning has been standing for days, read it properly once.** Three
   hits stood for days and one of them was the gate being wrong. Standing
   warnings need a scheduled read, not an ambient one.

4. **Prefer a redirect to a new page** when an existing page already serves the
   intent. Recording this because building the rooms index was the tempting
   move and would have created a duplicate.

## Addendum: ops/ had no CI at all, and the first run found two more

Chasing why my `preflight.py` change had not been validated, I found that
**nothing under `ops/` has ever been verified on push.** "Publish site image" is
the only workflow that runs preflight, and it is correctly filtered to
`site/**`, because `ops/` is not in the image. So the code holding every quality
gate, the dashboard Phil reads, and the checks that watch revenue was the one
part of this repository with no continuous integration.

That gap had already been paid for twice, and I had treated both as one-off
mistakes rather than as evidence of a missing control:

- a rebase committed unresolved conflict markers into `preflight.py`, killing
  every gate in the file, in a commit that was adding a gate
- a heredoc wrote two control bytes into a regex in the same file today

Both landed on main. Neither triggered a run.

The new `checks.yml` runs on `ops/**`: everything compiles, preflight, the
catalogue drift audit, and a check for control characters in source. **That last
check found two more instances of the same corruption on its first run**, both
weeks old:

- `generate_zone_heroes.py`: `0x08` where `\b` belongs, so the trailing
  "Zone"/"Area"/"Storage" was never stripped from the subject sent to the image
  model
- `wire_zone_heroes.py`: the same byte, so a leading noun was never trimmed from
  a zone photograph's alt text

Neither raised an error. Both simply did less than they said, silently, for
weeks. **Three instances of one defect class, in one day, two of which I had no
idea existed.**

I checked the output before deciding what to do about it, rather than assuming
the fix implied a rebuild. No zone page carries the leftover noun in its alt
text, because the loop above that guard already handled every real case. The
image prompts did carry the extra word, but approval climbed 46% to 96% with it
present and all 110 images are reviewed and approved, so regenerating them to
delete one word would be churn against no evidence of harm.

**The lesson I actually want to keep:** when I make the same mistake twice, the
correct response is not to be more careful, it is to build the thing that
catches it. Both earlier incidents got a careful commit message and no control.
The control took twenty minutes and found two more within a minute of existing.
