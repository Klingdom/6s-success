# Cycle 38 retrospective

**Shipped:** every page now tells a visitor where they are in the nav. Before
this, one page did and 185 did not.

## What went well

**The question from cycle 37 kept paying.** Last cycle found a missing footer
link by comparing like pages *to each other* instead of each to a standard.
Running the same question on headers found `contact.html` differing from the
other 185. The instinct was to call it drift and normalise it away. It was the
opposite: `contact.html` was the only page doing it right. Had I "fixed the
outlier" I would have deleted the one correct thing on the site.

**The CSS was already there.** `site.css` has styled
`.nav a[aria-current="page"]` with a terracotta colour and a 2px underline since
the design system was locked. For 186 pages it had nothing to attach to. The
design system anticipated this feature; only the markup was missing. Worth
remembering that a gap can sit on either side of a contract.

**I predicted the regression before making it, then measured it anyway.** The
generators copy chrome from `resources.html`. Marking `resources.html` would
make every generated page claim to be Rooms. I said so, then ran a rebuild
rather than trusting the reasoning: **135 zone and room pages** claiming to be
Rooms. Predicting a failure is not the same as knowing its size, and the number
is what justified chaining the pass into all five generators.

**I looked at the mobile rendering instead of reasoning about it.** The desktop
marker is a 2px bar under the link. Rendered at 390px with the menu forced open,
that bar spans the full menu width and sits *between* "Cards and book" and "Get
help" — it reads as a section divider, not as "you are here". No amount of
thinking about the CSS would have produced that; the screenshot produced it in
one look. It is a left rail on mobile now, which also keeps the marker from
depending on colour alone.

**The gate was proved before it was trusted.** Removed the mark from
`book.html`, watched `gate_nav_current` fail, restored it, watched it go quiet.
Then made that permanent as the sixth case in `test_gates.py`. A gate that has
never failed is not a gate.

## What did not

**The same defect class caught me again, in the same cycle it was named.** My
CSS edit asserted on an anchor string and threw. The re-render then ran anyway
and printed `clean at 390px` — a confirmation of a change that did not exist. I
only noticed because the traceback was above it. That is exactly *a run that
could not look writing its ignorance over a measurement*, and it happened
inside a sequence where I was actively watching for it. The cause was banal:
I copied the indentation out of my own `sed 's/^/  /'` display prefix, so the
anchor carried two extra spaces. **Display formatting is not file content.**

**`pytest ops/tests -q` reported "no tests ran" and I nearly took it as a
pass.** The suites are plain scripts, not pytest cases. Running them properly,
all twelve pass. CI already does this correctly, with a comment explaining why —
past-me had found it. Zero collected is not green.

**The outage is on day eight** and moved not at all this cycle. Six payment
links dead, `$19` against `$20,000`. Everything above is real customer value and
none of it is revenue. The single click that would change that is still Phil's.

## What to change next cycle

1. **Never take an anchor string from formatted terminal output.** Read the
   exact bytes (`grep | cat -A`) or match on a substring that cannot carry
   decoration. This cost two attempts today and the failure mode was silent.
2. **When a tool prints a result after a step that errored, treat the result as
   void.** Sequence success is not step success. The shoot said "clean" because
   it genuinely rendered — the old file.
3. **Keep running the like-to-like comparison outward.** Headers and footers are
   done. Left: `<head>` blocks (meta, canonical, JSON-LD), skip links, and the
   `<main>` landmark. Each is a contract that no single page owns, which is the
   precise condition under which the last two defects survived for months.
4. **The question that found both:** not "does this page match the standard?"
   but "why do these two pages that should be identical differ?" — and when one
   differs, ask which one is right *before* normalising.
